# Workflow

## 方法论

Conductor 的 **Context → Spec & Plan → Implement**。规则库、流程、模板的任何变更一律走 track，不直接零散改文件。

## Git 约定

- 项目起步第一件事：`git init`
- 分支命名：`track/{track-id}`
- 提交格式：`type(scope): message`（如 `feat(rules): 新增壁厚类规则 12 条`）
- 每个 phase 完成后提交 checkpoint，并在 plan.md 记录 SHA

## 质量门

| Gate | Requirement |
|---|---|
| 规则准入 | 每条规则必须有：编号、适用条件、推荐值区间、来源标注。来源分两类：**A 类**=国标/行标、材料商 datasheet 与设计指南、模具手册（标标准号或手册名）；**B 类**=行业通用经验值（标"经验值，建议结合实际验证"）。A 类占比 ≥60%，禁止无标注的裸数值，数值**不得**凭模型记忆填写 |
| 意见引用 | 评审意见必须引用规则编号；找不到依据的判断一律标 D 类（存疑，需人工确认） |
| 回归测试 | `fixtures/` 保存脱敏测试案例（含预埋问题清单）；SKILL.md 或规则库变更后必须重跑，对比命中率/误报率 |
| 免责边界 | 意见单固定附带："本意见单为辅助评审，最终以人工高级工程师确认意见为准" |
| Skill 校验 | SKILL.md 结构变更后用 skill-creator 复核触发可靠性 |

## 验证流程

1. 每条新规则先在 fixtures 案例上试评
2. 对照预埋问题清单统计命中/误报
3. 指标不达标先修规则库，再改流程
